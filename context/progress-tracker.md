## Architecture Decisions

- `bg-base` is declared as a standalone `@utility` in `app/globals.css` instead of a normal `@theme` color token. Registering "base" as a `--color-*` theme key silently turns Tailwind's `text-base` (font-size: 1rem) into a text-color utility, which broke font-sizing on shadcn's own Card/Dialog titles. The `@utility` form avoids the collision but does not support the `/alpha` modifier (e.g. `bg-base/95` from `20-ai-sidebar-shell.md`) — revisit if that's needed later. Every other custom token (`surface`, `elevated`, `subtle`, `brand`, `ai`, etc.) is a normal theme color since none of those names collide with a reserved Tailwind scale key.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` were added to `.env.local` (as `/sign-in` / `/sign-up`) as part of 03-auth even though `03-auth.md` calls them "existing" env vars — they weren't present before this change. Treated as Clerk's own standard var names (not app-invented custom vars), so adding them doesn't conflict with "use existing Clerk env vars, don't invent new ones."
- 03-auth uses Clerk's `dark` theme (`@clerk/ui/themes`) per the explicit spec instruction, not the `shadcn` theme the `clerk-custom-ui` skill otherwise recommends by default when `components.json` is present. The `dark` theme's `variables` are still fully remapped onto this app's CSS tokens in `lib/clerk-appearance.ts`, so Clerk's visual language (spacing/type scale) comes from `dark` but all colors come from the app palette.
- `/editor` is now implemented (04-project-dialogs): editor home + Create/Rename/Delete project dialogs and sidebar actions, all backed by in-memory mock data via `hooks/use-project-dialogs.ts`. No persistence or API routes yet — that's out of scope until a future spec wires it to Prisma/Vercel Blob per `architecture-context.md`.
- `prisma.config.ts` originally only did `import "dotenv/config"`, which loads `.env` alone. This project's real `DATABASE_URL` and Clerk keys live in `.env.local` (per the 03-auth precedent), and `.env` is just Prisma's untouched generated template (all comments, no values) — so `prisma migrate dev` failed with "datasource.url property is required" until `prisma.config.ts` was changed to explicitly load `.env` then `.env.local` (with `override: true`) via `dotenv`'s `config()`, matching Next.js's own `.env.local`-overrides-`.env` precedence. Next.js itself already loads both automatically (confirmed by `next build`'s own "Environments: .env.local, .env" log line) — this fix only affects the Prisma CLI/config path.
- 07-wire-editor-home lets `POST /api/projects` accept an optional client-supplied `id` (validated against `/^[a-z0-9-]+$/`) so the project ID and the Liveblocks room ID stay aligned (`roomId = slugify(name) + "-" + shortSuffix`, generated in `hooks/use-project-actions.ts`). This does not contradict 06's "do not add sequential IDs" — the id is a slug, not a sequence — and the schema's `cuid()` default still applies when no `id` is sent (e.g. `Untitled Project` from a blank name has no slug, so the hook omits `id`). The persisted `Project` has no `slug` column; `types/project.ts` `Project` dropped its `slug` field (UI never read it — the create dialog's live preview comes from the hook).
- 07-wire-editor-home: `/editor/page.tsx` became a server component; all client wiring (sidebar open state, `useProjectActions`, dialogs) moved into `components/editor/editor-shell.tsx`. `lib/projects.ts` `getUserProjects()` returns `{ owned, shared }` — owned by `ownerId === userId`, shared by `collaborators.some.email === primaryEmail` (via Clerk `currentUser()`), excluding owned. `lib/mock-projects.ts` and `hooks/use-project-dialogs.ts` were deleted.

- 06-project-apis makes `/api/projects(.*)` a "public" route in `proxy.ts`. This does not make the data public — every handler still calls `auth()` and returns `401` without a `userId`. It only stops `clerkMiddleware`'s `auth.protect()` from short-circuiting unauthenticated API fetches with a `404` (its behaviour for non-page requests), which would violate the spec's "unauthenticated requests return `401`".
- `prisma/schema.prisma`'s `generator`/`datasource` blocks (provider `prisma-client`, output `../app/generated/prisma`) predate 05-prisma and were left as-is since the spec only asked to add models/client/migration, not restructure the existing generator config — even though `architecture-context.md` describes generated client output as living under `prisma/`. Revisit if that inconsistency needs reconciling later.
